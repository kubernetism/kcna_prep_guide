Cloud Native Shared Responsibility Model
Traditional IT
Responsibilities split across multiple specialized teams:
App Team → Applications, Runtime
Data Team → Data
Middleware Team → Middleware
Infrastructure Team → OS, Virtualization, Servers, Storage
Network Team → Networking
Characteristics:
High barrier to entry
Costly to change
Scaling limitations
Closed to innovation
Hybrid IT
Teams begin blending responsibilities with DevOps practices.
Key characteristics:
Large overlaps between teams
Battles for control
Harder communication
Deep coupling of systems
Cloud Native IT
Shared responsibility across cross-functional teams:
Developers → Applications, Data, Runtime
Platform Engineers / Tiger Teams → Middleware, OS
Site Reliability Engineers (SREs) → Infrastructure & Operations
Security Engineers → Security controls
Network Engineers → Networking
Key practice: GitOps
Characteristics:
Low barrier to entry
Inexpensive to change
Exponential scaling
Open to innovation
Cloud Responsibility Evolution
On Premise → IaaS → PaaS → CaaS → FaaS
Direction:
Reduced vendor lock-in risk
Lower innovation cost
Faster time to market
Fact-Check Notes:
CaaS (Containers as a Service) and FaaS (Functions as a Service) are current, relevant service models.
GitOps is an active, modern practice (no deprecation).
Traditional IT team breakdown still aligns with current exam contexts for shared responsibility comparisons (AWS, Azure, GCP).
